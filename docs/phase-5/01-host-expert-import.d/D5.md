## D5: LimitMEMLOCK on the plan surface (profile/plan.rs)

Status: code + doc, offline. No GPU run, no live service touched.

### What changed

- `crates/breccia-profile/src/plan.rs`: `plan_text(profile, expert_pin_bytes: Option<u64>)`.
  When `Some(bytes)` the `--dry-run-plan` output gains a host-expert-import block:

  ```
  Host expert import (--host-expert-import ON)
    imported arena pin: 16.0 MiB → units need LimitMEMLOCK=infinity
  ```

  The verdict is derived from the number, not asserted: up to 8 MiB it reads "fits the
  default 8 MiB mlock limit", above it "units need LimitMEMLOCK=infinity".
- `crates/breccia-cli/src/main.rs`: both `profile --dry-run-plan` call sites pass `None`
  (breccia-profile has no engine accounting; wiring the real arena `pin_bytes()` into the
  CLI is D4, which imports the arena).

### Why a parameter, not a lookup

`breccia-profile` depends only on `breccia-vk`; it must not reach into
`breccia-engine` for D2's `HostArena::pin_bytes()`. The pin figure is an input the caller
already knows at plan time, so it is passed in. `None` means the flag is OFF.

### LimitMEMLOCK requirement (restated, unchanged)

The box grants 8 MiB soft/hard RLIMIT_MEMLOCK (verified with `ulimit -l` → 8192 KiB), so any
arena of a few MiB or more fails `mlock` and D2 degrades to the host lane. To run with
`--host-expert-import` on, the service unit needs `LimitMEMLOCK=infinity`; the engine must
not be run as root for CAP_IPC_LOCK. The plan text already carried this on the Tier-2 line
(`plan.rs:168`); the new block states it against the actual imported-arena figure.

### Test

`crates/breccia-profile/src/plan.rs::tests::plan_reports_expert_pin_only_when_flag_on`:
flag ON with 16 MiB prints the pin and the `LimitMEMLOCK=infinity` requirement; 4 MiB prints
the fits-under-default line; `None` prints neither. The existing
`plan_contains_roles_tiers_and_constraints` now also asserts the block is absent when OFF.
