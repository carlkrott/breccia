# 29 — Model loading and checkpoint I/O: what ports to Breccia's loader

Round 29, 2026-10-28. Read-only research: no GPU work, no model load, no build, no commit. Scope: how ServerlessLLM, IBM fastsafetensors and the Run:ai Model Streamer load checkpoints, and which of their designs fit Breccia's expert loading on the RX 6950 XT (gfx1030, RADV), the MI50 (gfx906, RADV), a ~30 GB host RAM budget, and a 70.6 GiB two-shard IQ3_XXS GGUF.

Citation convention: a bare path is in this repo at base `60a4799`; `:` gives a line. Short names: **doc 02** = `docs/phase-2/02-format-loader.md`; **untried-levers** = `docs/phase-4/02-untried-levers.md` (doc 27 cites this file as "doc 02" for its routing lines; C15); **doc 09** = `docs/research/09-zero-copy-host-memory-and-ggml-vulkan.md`; **doc 15** = `docs/research/15-lmcache-mooncake-tiered-kv.md`; **doc 24** = `docs/research/24-moe-offload-mixed-precision-experts.md`; **doc 27** = `docs/research/27-prefill-pipeline-and-et-vk.md`; **phase-2/01** = `docs/phase-2/01-transfer-harness.md`; **phase-0/04** = `docs/phase-0/04-host-memory.md`; **BRIEF** = `docs/BRIEF.md`. ## §0 Verdict

No new loader is needed. Breccia's current shape (30 blocks resident in the VRAM arena, 18 streamed on the host CPU lane, GGUF shards mapped read-only) is sound. The gaps are in what the page cache holds and how the cold path reads. Ranked:

1. **Drop the arena's source pages after upload, and hint the expert ranges.** No format change. If the mapping's pages stay resident, the page cache holds 41.69 GiB against a ~30 GB host budget (derived, §1; residency not measured, §6).
2. **Pin the 14.99 GiB streamed set in place with mlock on the file mapping**, not an anonymous copy. Gate: major faults and MemAvailable.
3. **Cold start: O_DIRECT, page-multiple, chunked io_uring reads with a queue-depth sweep.** New code; the engine has no such read path (C11). Gated on the owner's weights-volume decision (Q1).
4. **A frequency-ranked, 4096-stride expert sidecar**, only if card 2 cannot hold the set and a routing histogram shows real skew. The routing evidence conflicts and its sourcing is partly unstated (C14), so the gain is unknown.
5. **RX-only zero-copy read of a host-imported arena** (the doc 27 card 2 re-test). This is a compute-path question owned by doc 27's gate, not an I/O loader change. The MI50 is out of the first wave.

Not ranked:

- CPU-lane overlap (the lane and H2D sharing host DRAM): no measurement here (card 6, gate only).
- ServerlessLLM, fastsafetensors and Run:ai port as ideas only. The platform does not reject them on its own: ServerlessLLM documents AMD ROCm support, fastsafetensors has a hipFile path in code, and Model Streamer has S3, GCS and Azure backends (§2b). They are rejected as loaders because adopting any of their checkpoint formats means rewriting the GGUF shards, which the brief forbids (R9), and ServerlessLLM's DRAM and SSD tiers duplicate the arena and page cache (R3).

Disk tier: the live shards sit on an NVMe-backed btrfs volume (findmnt, read-only; C4), against the brief's "never NVMe for weights". §1 gives cold-start numbers for both cases. The token path must be RAM-resident either way.

Code facts (line numbers in the pinned clones; `file` is the path inside each repo):

- **ServerlessLLM.** The index (`sllm_store/sllm_store/torch.py#L49–L80`) has no GPU id. Partitions roll at 10 GiB (`sllm_store/csrc/checkpoint/tensor_writer.h#L26`), and records pad to 8 bytes (`sllm_store/csrc/checkpoint/tensor_writer.cpp#L27–L41`). Tiers: disk partitions, then a pinned DRAM pool (aligned 4 KiB, then cudaHostRegister, `sllm_store/csrc/sllm_store/pinned_memory_pool.cpp#L25–L41`), then GPU. No S3 or remote code in `sllm_store` (grep, read-only). Eviction is whole-model LRU (`sllm_store/csrc/sllm_store/checkpoint_store.cpp#L111–L172`). Read: O_DIRECT open, reopened buffered on EINVAL (`sllm_store/csrc/sllm_store/model.cpp#L96–L105`). One thread per contiguous chunk range, each a synchronous pread at depth 1 (`model.cpp#L127–L146`, `#L176`). No io_uring, libaio, fadvise, madvise or mmap hits (grep, read-only). Defaults: 4 threads, 32 MB chunks, 4 GB pool (`sllm_store/sllm_store/cli.py#L173–L181`). Per-GPU copy is synchronous cudaMemcpy (`model.cpp#L327–L332`). AMD support is documented (ServerlessLLM `docs/intro.md#L14`; `sllm_store/README.md#L149`, labelled experimental) with a ROCm build branch (`sllm_store/setup.py#L71`). The copy path is cudaMemcpy, so a ROCm build is unchecked here.
- **fastsafetensors.** Loads standard safetensors directly, with no cache tier. The default copier is gds, but on AMD, when a device memory budget is set and hipFile budget support is absent, it falls back to nogds (`fastsafetensors/copier/gds.py#L509–L522`). O_DIRECT is on for ROCm (`fastsafetensors/copier/gds.py#L75–L76`); ALIGN is 4096 (`fastsafetensors/cpp/ext.cpp#L127`). nogds: 16 threads (`fastsafetensors/copier/nogds.py#L310`), a 16 MiB bounce buffer (`fastsafetensors/copier/gds.py#L447`), 2 buffers per thread so 32 slots (`fastsafetensors/cpp/ext.cpp#L864`, `#L1051`), and block size = bbuf ÷ slots = 512 KiB per pread (`#L1052`). Each slot has its own copy stream and cudaMemcpyAsync H2D (`#L952`, `#L1073–L1077`), and a slot's DMA is synced before reuse (`#L980–L985`). gds: 16 workers by default (`fastsafetensors/copier/gds.py#L448`), each calling cuFileRead (`fastsafetensors/cpp/ext.cpp#L1252–L1254`). No io_uring or liburing. TP is file ownership per rank (`fastsafetensors/parallel_loader.py#L284–L300`), with byte-range reads only in chunk plans (`fastsafetensors/loader.py#L265–L276`).
- **Model Streamer.** Strategies are `io_uring_direct`, `libaio_direct`, `sync_buffered` (`cpp/streamer/impl/config/config/config.h#L121`). Defaults: async queue depth 64, node-wide and the same at TP=1 and TP=8 (`config.h#L77–L78`); async chunk 8 MiB (`config.h#L75`); direct block 64 KiB (`cpp/posix_io/alignment/alignment.h#L60`); `default_concurrency` 16 (`config.h#L106`; its use was not traced). Python passes CPU as the device to the native reader (`py/runai_model_streamer/runai_model_streamer/libstreamer/libstreamer.py#L189–L192`), so the native async device-copy path is not reached from Python. Reads land in a non-pinned numpy ring, and the consumer copies to GPU (`py/runai_model_streamer/runai_model_streamer/file_streamer/requests_iterator.py#L150–L153`, `py/runai_model_streamer/runai_model_streamer/file_streamer/file_streamer.py#L320–L334`). Its CUDA device code is under `cpp/device/cuda`, and the clone has no ROCm, HIP or AMD reference (grep, read-only), so its AMD status is unconfirmed (§6). Its build produces `libstreamers3.so`, `libstreamergcs.so` and `libstreamerazure.so` (`README.md#L174–L176`).

## §3 Rejected ideas

- **R1. NVMe as an expert-miss tier.** The brief rules out NVMe for weights. doc 09:161–192 (the A3 section, NVMe as a miss path) and doc 24:32 and :140 (the ≥296 µs NVMe miss floor at the brief's 5.9 GB/s, not re-measured) assume that tier, so their miss costs do not apply here.
- **R2. GPUDirect Storage (cuFile) and hipFile.** cuFile needs CUDA and an NVIDIA device. hipFile is the AMD counterpart, selected on HIP in fastsafetensors (`fastsafetensors/cpp/ext.cpp#L385`, `#L417–L426`). The reason to reject it here is the engine, not the platform: Breccia's device path is Vulkan on RADV with no HIP runtime, and its device buffers are Vulkan allocations (`crates/breccia-engine/src/xfer.rs:85–87`). Its flag surface names HIP only as a llama.cpp-compatible hint (`crates/breccia-flags/src/lib.rs:1–4`, `:29`). hipFile moves data into HIP device memory (general hipFile behaviour, not pinned here), so a passing hipFile test on gfx1030 would not by itself reopen R2. Whether hipFile works on gfx1030 or gfx906 is a secondary unknown (§6).
- **R3. ServerlessLLM's loader as a unit.** Its checkpoint format and DRAM/SSD tiers duplicate Breccia's arena, host lane and page cache. Adopting its format means rewriting shards (forbidden). Keep only the chunked-read idea (card 3).
- **R4. fastsafetensors tensor-parallel sharding.** Breccia's split is by block, not by tensor, so TP sharding has no target here. The format is also safetensors, not GGUF.
- **R5. Run:ai object-store concurrency.** No object store is in play. Local-file concurrency is card 3's QD sweep.
- **R6. Anonymous copy of the streamed set as the default.** It duplicates 14.99 GiB during the copy and then holds it twice. Use it only if card 2's file-backed mlock fails (Q3).
- **R7. Per-expert O_DIRECT from the GGUF or from `experts.bin`.** Neither is page-aligned per expert. The GGUF stores each expert's gate, up and down as three role-major tensors that are not adjacent in the file (doc 02 §2.1). `experts.bin` strides by `blob_bytes` with no padding (`pack.rs:525`), and the sampled blobs are 456.25 / 318.75 / 531.25 pages (derived). A page-unaligned read is partly served from cache and reports about 2× the device (doc 09:173–176).
- **R8. Relying on the kernel page cache alone under a memory cap.** The engine already documents that co-tenants thrash the page cache the lane reads through (`crates/breccia-engine/src/model.rs:1354`). That page cache is charged to the cgroup is unpinned (§6). Residency is not guaranteed without card 2's lock or card 1's trimming.
- **R9. Rewriting GGUF shards.** Forbidden by the brief. Card 4 writes a sidecar instead.
- **R10. MI50 zero-copy as the first card.** The MI50 link is x4 at its upstream bridges (C1), its zero-copy path is unmeasured, and BRIEF:141 makes it the headless card. Card 5 is RX-only for this reason.
- **R11. Mooncake's io_uring store as a template.** Its default is `use_uring=false` (doc 15:51), and its aligned-buffer constant disagrees with its own comment (doc 15:158; C12). Copy neither.

## §4 Conflicts

- **C1. MI50 link width.** doc 09:12 reports "gen3 x16" for the device link and does not mention the bridges. phase-2/01:78 and BRIEF:126 say gen3 ×4. Live sysfs: the MI50 device link is x16 (max), but its two upstream bridge hops have max width x4, and both read at 2.5 GT/s negotiated at the instant read. The max-x4 bridge topology is the likelier explanation for the measured 2.71–2.85 GB/s (phase-2/01:199) than the harness theory in doc 09:154–156, which calls 2.84 GB/s "a harness artefact". Not measured here.
- **C2. Display card.** doc 09:10 calls the RX "HEADLESS"; doc 09:22 and :156 call the MI50 the display card. BRIEF:141 and :225–226 say the RX drives the displays and the MI50 is headless. Live sysfs: the card with boot_vga=1 is the RX (16 GT/s x16). doc 09 is stale here.
- **C3. MI50 overlap.** BRIEF:126 says "~0 % overlap". phase-2/01:111 gives 58.1–58.5 %; :151 gives 61.8–63.6 %; :201 gives 58.1–58.5 % for the 4/16 MiB bursts and 0.8–2.1 % in the phase-0 column. The brief's figure matches only the phase-0 shape.
- **C4. Weights location.** The brief says "never NVMe for weights". The live shards sit on an NVMe-backed btrfs volume (findmnt: btrfs, NVMe partition). The volume had 91.3 GB free (85.0 GiB) and 89 % used at read time (df, read-only). doc 02 §4's command reads the same shard directory (path not copied here). This is the owner decision in Q1.
- **C5. Shard total.** doc 02:162 and :177 give 75,828,974,080 B; the live sum is 75,839,998,528 B, a difference of 11,024,448 B. "75 GB" in BRIEF is decimal rounding of the same order, so the units are not in conflict; the byte difference is. Cause not checked (possibly a shard revision).
- **C6. Per-expert blob constant.** doc 24:30 and doc 27:40 use 1,746,133 B as a per-use blob. It is the mean over 48 layers. Per-layer blobs run from 1,305,600 B (blk.1) to 2,176,000 B (blk.47) (doc 02:191–194). Miss-cost figures built on the mean are averages, not per-miss costs.
- **C7. Streamed block count.** BRIEF:79 says 18 streamed, 30 resident. doc 27:133 (item 5) cites doc 01 §8ag at 39 streamed, 9 resident. This doc uses BRIEF's 18 and says so; card 2's lock size depends on it (Q7).
- **C8. SATA as Tier-3.** phase-0/04:26 says Tier-3 "belongs on" the agent-storage SATA mount, for capacity. BRIEF:145 calls that volume the "wrong place for an expert tier" at 0.39 GB/s, and doc 09:185 measures 332–390 MB/s cold. phase-0/04 is stale on expert streaming.
- **C9. Read-ahead.** BRIEF:143 says a timer pins btrfs read-ahead to 128 KiB and loops over btrfs devices only. doc 09:190 records the btrfs read-ahead back at 8192 KiB, with the 128 KiB fix not persisted (doc 09:440). doc 09:190–191 calls an 8 MiB read-ahead "9× read amplification" for the 462 KiB reads. Live: the SATA block device's read-ahead is 8192 KiB and no timer covers it. Any SATA weights volume would run at that value, so this is a gap, not only a doc conflict, and it becomes live if the weights move (Q5).
- **C10. Zero-copy projection.** doc 09:85–88 projects "YES, at 22–26 GB/s". doc 09:27–30 records a negative BAR measurement. doc 27:136 flags the same pair; the projection is not a measurement.
- **C11. "io_uring-fed ring" is a description.** `crates/breccia-vk/src/transfer_bench.rs:175, 566` describe a steady state with an io_uring-fed pinned ring. A grep of `crates/breccia-engine` and `crates/breccia-format` for io_uring, O_DIRECT, madvise, mlock, fadvise, pread and read_at finds nothing. The only io_uring code is probing: `crates/breccia-profile/src/system.rs:136–160` (sysctl) and `:298` (O_DIRECT). Card 3 is new code.
