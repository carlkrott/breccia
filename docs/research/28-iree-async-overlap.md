# 28 — IREE and Kompute async submission: what reaches Breccia's fence waits

Round 28, 2026-10-28. Scope: how IREE and Kompute keep the host from blocking on GPU fences while work is in flight, mapped to Breccia's decode path (`Multi`, two streams, one device per stream: RX 6950 XT on RADV gfx1030, MI50 on RADV gfx906). The round brief reports 146-152 ms per stream-token at `--streams 2`, `shared-exp` 44.7-66 ms and `wait-gpu` 8.8-28 ms per step, and proposes that the host blocks on a GPU fence inside the shared-expert span. Read only: no code change, no GPU work, no model load, no build. IREE and Kompute were read through WebFetch summaries of upstream sources, not a pinned checkout. Engines the brief lists as already covered were not re-audited.

Citation convention: a bare path is in this repo at base `5c7b54e`; `L` or `:` gives a line in that file. `crates/` paths are Breccia code. Upstream sources are named by project and file and were read on 2026-10-28. Every number is cited (file and line) or derived (arithmetic in §1). Any number that is neither is marked `UNVERIFIED - requires the GPU qualification card`.

Short names: **doc 01** = `docs/phase-4/01-forward-pass.md`; **doc 08** = `docs/research/08-submits-and-deepspeed.md`. Other docs are spelled out in full: research doc 02 = `docs/research/02-vulkan-followups-and-powerinfer.md`; phase-4 doc 02 = `docs/phase-4/02-untried-levers.md`. Cards are Card 1, 2 and 3. "The brief" is the round 28 brief. A bare `UNVERIFIED` below is shorthand for `UNVERIFIED - requires the GPU qualification card`, the marker the brief requires.

## §0 Verdict

**Gate 0, before any card is scheduled.** On the code path, the brief's `shared-exp` figure is a timer attribution: it contains the peer stream's fence wait, lane and submit, not a fence inside stream A's own shared expert. `Timers::mark` charges the time since the previous mark to the stage that the previous mark set (`crates/breccia-engine/src/graph.rs:156-168`). For a host-lane block, the last mark in `submit_block` is `SHARED`, set by the dense prelude (`graph.rs:2039`). That stage runs until the stream's next mark, `WAIT_GPU` at the top of its next `finish_block` (`graph.rs:3001`). In between, `token_all` runs the other stream's `finish_block` and `submit_block` (`crates/breccia-engine/src/multi.rs:192-208`). The peer's fence wait (`graph.rs:3017-3026`), lane (`graph.rs:3135`) and submit all fall inside A's span. A's own shared expert costs 0.10-0.15 ms/token (doc 01 §8ad, `docs/phase-4/01-forward-pass.md:2479-2500`; §8ae, `:2544-2556`). The same artifact class was found and fixed on the chunk path: §8ae puts a `mark(WAIT_GPU)` before the pass-1 flush (`:2548-2550`). The decode `Multi` path has no such fix. Card 1 confirms or refutes this.

**Retraction.** An earlier plan said a constant `shared-exp` + `wait-gpu` sum separates the gap model from a fence inside the span. It does not: both models predict the same total host-blocked time per token (§1 item 4). Nothing in this doc relies on that claim. The discriminating evidence is the code path and Card 1's instrument.

**The real host stall is in a different place, and the deferral does not remove it.** A placed block (experts resident, no host lane) leaves its segment in flight (`graph.rs:3014-3016`). The next block's `submit_block` calls `ensure_batch` (`graph.rs:1918`), which calls `flush()` (`graph.rs:1240`), which waits the pending segment (`graph.rs:1165-1177`) before any new work is recorded. So the first waiting flush is in `submit_block(b+1)`, not in `finish_block(b)`. The comment at `graph.rs:3006-3013` says the deferral lets the host record block b+1 while block b executes. On a single session that is not what happens. What the deferral does is move the wait past whatever runs between the two calls, which under `Multi` is the peer stream's turn. Doc 01 §8bh measured this on one stream: `wait-gpu` 30.8 → 10.2 ms/token, token time unchanged (`docs/phase-4/01-forward-pass.md:5694-5745`). About 20.7 ms/token of host wait is still there (§1 item 6).

**What IREE does that Breccia does not.** IREE's `queue_execute` takes a wait-semaphore list, so a submission can depend on earlier GPU work without the host waiting (§2 row 1). Breccia's `end_submit` takes only a signal (`crates/breccia-kernels/src/dispatch_batch.rs:950`), and `submit_cmd` takes no wait list (`crates/breccia-vk/src/ctx.rs:1458-1463`). For a same-device chain, Breccia can express the dependency without a wait semaphore: the batch's closing barrier, recorded into the predecessor's command buffer (`dispatch_batch.rs:976-980`), ordered against the later submission on the same queue. That is the barrier route (Card 2). A wait-semaphore path is needed only for cross-device work, which `Multi` does not allow (`multi.rs:140-144`) and which this doc does not recommend (§5 f, g). The barrier route depends on RADV ordering behaviour that has not been measured (`UNVERIFIED - requires the GPU qualification card`).

**Ranked cards.** Card 1 goes first, because the other cards cannot be gated until the brief's attribution is fixed.

1. **Card 1: re-anchor the peer's time out of `Multi`'s stage timers (measurement only).** Helps RX, MI50 and CPU equally in throughput terms, which is none. It makes each stream's own `wait-gpu` and `shared-exp` its own. Change: one `Timers` re-anchor (discard now − last without charging a stage) at the start of each `finish_block` in `token_all` (`multi.rs:199`). The discarded gap is already measured by `t_finish` and `t_submit` (`multi.rs:205-206`). **Accept gate:** per-stream `SHARED` ≤ 0.2 ms/token (baseline 0.10-0.15, §8ad and §8ae); the discarded gap equals the peer's `t_finish` + `t_submit`, summed over both streams, within ±5%; token wall time within noise; output bit-identical; 32/32 greedy.

2. **Card 2: barrier route for same-device placed-block chaining (conditional on Card 3's record measurement).** Helps RX and MI50 for placed blocks on either card. CPU is freed only indirectly: the host stops waiting before it records. Change: in `flush()`, do not host-wait a deferred placed predecessor on the same device, neither the pending-segment wait (`graph.rs:1165-1177`) nor the `wait_all` after it (`graph.rs:1178-1182`), which waits the same fence; make its closing barrier unconditional for that segment; keep the host wait under the six conditions listed after the §2 table. **Pre-gate:** under `Multi`, after Card 1, the moved wait must be at least 1.6 ms/token (3% of 54.5 ms, §1 item 6). **Accept gate:** `wait-gpu` + `hc-write(ffn)` falls by at least half the moved amount (at least 10.3 ms/token on the single-stream baseline, §1 item 6); token time at least 3% faster at the same config (interleaved A/B, the §8n protocol); bit-identical; 32/32 greedy. Card 2's ceiling is set by record time (§1 item 8).

3. **Card 3: record-once decode chain and frozen command-buffer replay (conditional; helps CPU most).** Helps CPU directly (record and `t_submit` on the host thread) and RX and MI50 only indirectly (less host latency between submissions; the GPU work is unchanged). Its size is not settled: three doc 01 values disagree (§1 item 8, §4 item 5). **Measure first:** `batch_cmd::record_seconds()` (defined at `crates/breccia-kernels/src/dispatch_batch.rs:792`; used at `crates/breccia-cli/src/main.rs:1846` and `:2795`) at the `Multi` decode config, divided by streams × steps. **Gate:** proceed only if the measured record is at least 1.6 ms per stream-token. Then accept only if `t_submit` per stream-token falls by at least 50%, token time is at least 3% faster, output is bit-identical, and 32/32 greedy holds. Doc 01 `:3323-3329` puts replay last; the owner decides the order (§5 h).

**Not a card: fallback for Card 2.** A single-submission router marker (the host reads the router's ids from host-visible memory while the GPU continues into the shared expert, with no second submission) is the only other route to hide the shared expert. Its ceiling is about 3.4 ms/token (§1 item 9), `UNVERIFIED - requires the GPU qualification card`. It has not been built or measured.

**Gate baselines.** Each gate is 3% of the baseline stream-token time at the config under test: 1.6 ms at single-stream §8bh (54.5 ms), 3.0 ms at the §8y 32-thread gate (98.5 ms), 4.4-4.6 ms at the brief's `Multi` rate (146-152 ms).

## §1 Derivation

Every derived number below is arithmetic on a cited input. Items marked UNVERIFIED depend on a measurement that does not exist yet.

1. **Brief's aggregate rate.** Two streams at 152 or 146 ms per stream-token: 2 × 1000 / 152 = 13.16 and 2 × 1000 / 146 = 13.70 tok/s aggregate.

2. **Regime.** The canonical gate in doc 01 §8y is 20.3 aggregate tok/s at 32 threads (`docs/phase-4/01-forward-pass.md:2109-2124`): 2000 / 20.3 = 98.5 ms per stream-token. The 8-thread default row of the same table is 14.71 aggregate: 2000 / 14.71 = 136.0 ms. The brief's 146-152 ms is slower than the default. Which regime the brief measured is an owner question (§5 a, d).

3. **The brief's 44.7.** The 16-thread row of the §8y table is `16 | 16.99 | 55.2 | 44.7`, with columns aggregate, lane ms/step and fence ms/step (`docs/phase-4/01-forward-pass.md:2118-2124`). 44.7 is the fence column, not `shared-exp`. Either the brief used a fence number under the `shared-exp` label, or it came from a different protocol (§5 a).

4. **What `shared-exp` contains.** Let the two streams be symmetric, so each stream's `wait-gpu` equals the peer's, w. Then A's `shared-exp` = w (peer's wait) + P (peer's lane, transfer, submit and loop overhead) + A's own shared expert (0.10-0.15 ms). Under this model the total host-blocked time per token, `shared-exp` + `wait-gpu`, is 2w + P + own. Under the brief's own hypothesis (a fence inside the span) the same total is F + S + W. Both models predict the same total, so the sum does not separate them (§0 retraction). If the brief's pairs come from one run, P = 44.7 − 8.8 = 35.9 and 66 − 28 = 38 ms per step. That split is not measured (`UNVERIFIED - requires the GPU qualification card`). Card 1 separates the two.

5. **Peer gap vs. `t_finish` / `t_submit`.** In `token_all`, `t_finish` and `t_submit` time each `finish_block` and `submit_block` (`multi.rs:205-206`). The gap that A's `SHARED` absorbs is the peer's `finish_block` + `submit_block` + loop overhead. So after Card 1, Σ(peer `t_finish` + `t_submit`) should equal the discarded gap, within the loop overhead, whose size is UNVERIFIED.

6. **Moved placed-block wait.** Doc 01 §8bh gives `wait-gpu` 30.848 → 10.158 ms/token and 30.916 → 10.129 ms/token in its two columns (`docs/phase-4/01-forward-pass.md:5694-5745`). Moved wait = 30.848 − 10.158 = 20.69 and 30.916 − 10.129 = 20.79 ms/token, so about 20.7. Token means 54.53 → 54.76 ms (+0.4%, inside the spread of the two columns), so the move was neutral. Card 2 pre-gate: 3% of 54.5 = 1.6 ms/token. Under `Multi` the peer's work may already cover part of this wait, so the single-stream figure is an upper bound (§6).

7. **Per-wait cost.** §8bh: 64 waits per token, 531 µs each, = 34.0 ms/token, of which the `sum` (GPU execution) is 30.4 ms (doc 01 §8bh table). Doc 08 gives +8.6 µs wall per extra submit (`docs/research/08-submits-and-deepspeed.md:27`): 64 × 8.6 µs = 0.55 ms/token, which is 0.55 / 34.0 = 1.6% of the wait. Submit overhead is a small part of the wait; the wait is GPU time.

8. **Card 2 ceiling.** Host record of block b+1 can overlap GPU execution of block b. The saving per block is at most min(GPU wait of b, record of b+1), so the token saving is at most min(Σ record, 20.7 ms/token from item 6). The record cost has three values in doc 01, and they do not share a basis:
   - (a) §8g: 10.02 ms per 31-token run = 0.32 ms/token, at 1 353 dispatches/token (dual 20/28, 16 threads; `docs/phase-4/01-forward-pass.md:529-562`, the record line at `:539`). This is a different config. Ceiling = 0.32 / 54.5 = 0.6% of token time, below the 1.6 ms pre-gate.
   - (b) §8ao table: record 19.76 ms/token (per-batch sets) and 19.48 (persistent sets) at 5 167 dispatches/token, single stream, 30 blocks (`docs/phase-4/01-forward-pass.md:3254-3257`). Ceiling = min(19.5-19.8, 20.7) = 19.5-19.8 ms = 36% of token time. The §8ao text's "3.2 µs × 5 167, up to ~16 ms" (`:3267-3268`) disagrees with its own table: 19.76 / 5 167 = 3.8 µs.
   - (c) §8an: 32.52 ms/token (`:3201`). Its denominator is not stated. The census of 313 790 dispatches over 112 token-graphs (3 prompt passes × 27 + 31 decode, `:3177`) is 2 801 per graph, which gives 32.52 / 2 801 = 11.6 µs per dispatch (`:3205`). Over the 31 decode tokens it is 10 122, which gives 3.2 µs. Ceiling = min(32.5, 20.7) = 20.7 ms = 38% of token time.

   All three are upper bounds. Card 3's measurement decides which basis holds, if any.

9. **Single-submission router marker (fallback).** Shared expert GPU time after the router: 0.24 ms per block (doc 01 §8n, `docs/phase-4/01-forward-pass.md:857`). Lane slowdown from a concurrent segment: 0.17 ms per block (`:860`, measured with the two-segment variant). Net hideable: 0.24 − 0.17 = 0.07 ms per block; × 48 blocks = 3.4 ms/token. UNVERIFIED: the 0.17 was measured with the second submission in place, which a single submission does not have, and the router-marker variant was not built.

10. **Two-segment regression.** 139.7 − 121.9 = 17.8 ms/token = 14.6% of 121.9 (doc 01 §8n table, `:843-865`).

11. **Bubble vs. submit cost.** Doc 01 §8n: a GPU pipeline bubble of about 0.2 ms per block (`:843-853`). Doc 08: +8.8 µs GPU per extra submit (`:27`). Per token at 48 blocks: 0.2 × 48 = 9.6 ms vs 8.8 µs × 48 = 0.42 ms. The per-submit ratio is 200 / 8.8 = 22.7, about 23×. Conflict, §4 item 6.

12. **Timeline vs. fence (doc 08).** Doc 08 gives 17.3 µs per submit on a depth-2 timeline and 33.2 µs serialized, in a bare re-record loop (`docs/research/08-submits-and-deepspeed.md:236-237`). The difference is 33.2 − 17.3 = 15.9 µs per wait. × 64 waits per token = 1.0 ms/token: a ceiling for replacing every decode fence with a depth-2 timeline. UNVERIFIED for decode, because doc 08 measured the chunk path (`:206-242`).

13. **Brief's rate vs. protocol.** 13.16 and 13.70 aggregate are 0.648-0.675 × the 20.3 gate (13.16 / 20.3 = 0.648; 13.70 / 20.3 = 0.675) and 0.894-0.931 × the 8-thread default (13.16 / 14.71 = 0.894; 13.70 / 14.71 = 0.931). Only the owner can say which protocol produced the brief's numbers (§5 a).

Row 1 is the only mechanism that changes the answer to "does the host block on a fence for a dependency the GPU already resolves?" Breccia can get the same device-side dependency on one queue without a wait semaphore (Card 2), so row 6's device-side direction is needed only for cross-device work.

**Card 2 keeps the host wait unless all of these hold.**
1. Tracking is on: `BRECCIA_NO_BARRIER_TRACK` is unset (`track_disabled`, `dispatch_batch.rs:395-397`). With tracking off, `end_submit` skips the closing barrier (`dispatch_batch.rs:976`), so no cross-submission edge is recorded. The per-dispatch barrier that the disabled tracker forces (`dispatch_batch.rs:1496-1522`) is not checked as a substitute.
2. `BRECCIA_BARRIER` is not `none` (`crates/breccia-vk/src/ctx.rs:921-924`). Under `BarrierScope::None`, `barrier_compute_on` records nothing (`ctx.rs:1344`).
3. `BRECCIA_NO_DEFER_PLACED` is unset (`crates/breccia-engine/src/graph.rs:98-101`), and the segment is not traced (`graph.rs:3014`, `trace.is_none()`).
4. The successor's first read of the predecessor's output is a compute read. The Sync2 barrier covers COMPUTE to COMPUTE only (`ctx.rs:1351-1358`); transfer and host reads are not covered. Whether the first consumer, the next block's dense prelude, is compute is `UNVERIFIED - requires the GPU qualification card`.
5. The closing barrier is unconditional for that segment. Today it is recorded only when DIRTY is non-empty (`dispatch_batch.rs:976`). The unconditional barrier also covers write-after-read hazards, which DIRTY does not track (as read in `dispatch_batch.rs:966-980` and `ctx.rs:1351-1358`).
6. `flush` must skip both the pending-segment wait and `wait_all` (`graph.rs:1165-1182`) for that segment. `wait_all` waits every slot still in flight on the device, so skipping only the first leaves the host wait in place.

**`pending_seg` is one slot.** `pending_seg` (`graph.rs:515`) is set at `graph.rs:1162` and `:1216`. If the predecessor is not waited, the next submit overwrites it, so the segment must be collected by `wait_all` (`graph.rs:1178-1182`) or by the ring's slot reuse (`dispatch_batch.rs:833-870`). The comment at `graph.rs:3011-3012` says exactly that. Whether it holds under Card 2 is `UNVERIFIED - requires the GPU qualification card`. A host read of placed output must follow `wait_all`.

## §3 Rejected list

- **IREE native timeline replacing decode fences.** A depth-2 timeline saves 15.9 µs per wait in doc 08 (§1 item 12), about 1.0 ms/token at 64 waits, and that is UNVERIFIED for decode. Not worth replacing every fence.
- **A wait-semaphore path for same-device chaining.** The predecessor's closing barrier on one queue does the same job without a new `submit_cmd` argument (§0; §2 row 1). Kept only for cross-device work, which is not recommended.
- **IREE compiler-driven partitioning and affinity.** Breccia's placement is hand-written (`crates/breccia-engine/src/placement.rs:67` `layer_device`; placed branch at `graph.rs:1923-1935`). Adopting the compiler would also take its CPU path, and its llvm-cpu and local-task drivers are UNVERIFIED for Breccia's custom CPU dequant kernel. Not checked (§6).
- **IREE device groups and cross-device timeline handoff for a single-stream split.** Not the measured case. The hand-off flush (`graph.rs:1883-1887`) is a real stall, but the single-stream split was already rejected on placement evidence (doc 01 §8n). Sharing semaphores across VkDevices is UNVERIFIED.
- **Kompute `evalAsync` / `evalAwait`.** The same as Breccia's segment pattern (§2 row 4). No new mechanism.
- **Doc 01 §8n two-segment shexp split.** Measured 139.7 vs 121.9 ms/token (§1 item 10). Rejected.
- **Doc 01 §8n copies inside the block's batch.** Measured 139.7 vs 121.9 ms/token, about 0.36 ms of GPU and driver time per block (`docs/phase-4/01-forward-pass.md:866-883`). Rejected.
- **A second host lane thread.** The expert pool is one `Mutex` (`graph.rs:500` field; lock at `graph.rs:3135`) and the lane runs on the one host thread in `token_all`. Two lanes would contend for the same cores and the same lock. Rejected unless the pool is split (not checked).
- **GPU-side Vulkan events.** Measured as losers in research doc 02 (`docs/research/02-vulkan-followups-and-powerinfer.md:103-105`). No host-poll event measurement exists (§6).
- **Per-dispatch descriptor-set caching.** No delta (doc 01 §8ao).
- **Placed-block deferral as overlap by itself.** Doc 01 §8bh: neutral at single stream, `wait-gpu` moved and token time unchanged. Kept only because it is neutral and moves attribution. The overlap it was written for needs Card 2 or the peer stream.
- **Changing the `Multi` loop order.** The peer's wait already overlaps this stream's GPU work: in `token_all`, A's `submit_block(b+1)` (`multi.rs:202`) is queued before B's `finish_block(b)` (`multi.rs:192-199`). No change is proposed.
- **Single-submission router marker as a first choice.** Ceiling about 3.4 ms/token and UNVERIFIED (§1 item 9). Kept as the fallback if Card 2 is rejected.

## §4 Conflicts with existing docs (file:line)

1. **"Queue order" vs. the closing barrier.** `crates/breccia-engine/src/graph.rs:3008` says queue order "already guarantees the dependency", and doc 01 §8bh says "queue order already covers the dependency" (`docs/phase-4/01-forward-pass.md:5698`). `crates/breccia-kernels/src/dispatch_batch.rs:968-969` says "queue order alone does not make memory visible". Today the code enforces the dependency with the host wait in `flush` (`graph.rs:1165-1177`); the closing barrier (`dispatch_batch.rs:976-980`) is what makes the next submission's reads see the writes. Queue order without the closing barrier does not give visibility on either reading. The comment's claim can hold only once Card 2 supplies the barrier.

2. **Deferral comment vs. flush path.** `graph.rs:3010-3011` says the deferral lets the host "record block b+1 while block b executes". The first waiting flush is in `submit_block(b+1)` (`graph.rs:1918` → `:1240` → `:1165-1177`), before any recording. On a single session the claim is wrong. The `defer_placed_waits` doc comment (`graph.rs:91-96`) makes the same claim and cites "24.6 us of the 33.2 us"; doc 08 has no 24.6 figure (its nearest is "the 24 µs wait" at `docs/research/08-submits-and-deepspeed.md:240`), so that figure is UNVERIFIED. Under `Multi` the wait moves past the peer's turn, which is the real effect.

3. **HC_WRITE timing.** `graph.rs:3006-3013` says HC_WRITE is "recorded into the next submission". It is recorded in the same `submit_block(b)` as the MoE (`graph.rs:1926-1934`, `submit_batch` at `:1934`), before `finish_block(b)` runs. So "next" is wrong.
